## pqcm 节点处理

`pool-0013` 的 `pqcm` 节点在 hw-check 里报 WARN：
```
high DRAM correctable ECC count (>1000, GPU memory chip may have physical defect)
```

含义：
- **Correctable = 软错误**，被 ECC 纠正，不影响计算正确性
- **> 1000 个**：意味着某个 GPU DRAM chip 频繁位翻转，可能是物理缺陷早期表现（也可能是宇宙射线 / 温度 / 电压临时因素）
- 未到 `Uncorrectable ECC` 或 `retired pages` 级别，还没触发硬件 fault

三种处理方式（跟发起交接的人对齐）：
1. **接受 + 观察**：不 cordon，让业务方跑一段时间，看错误率是否恶化。追加 monitoring alert 到 `dcgm-exporter` 已经暴露的 `DCGM_FI_DEV_ECC_DBE_VOL_TOTAL` / `DCGM_FI_DEV_ECC_SBE_AGG_TOTAL` metric
2. **提前 cordon**：`kubectl cordon <node>`，让 pool-0013 变成 17/18 台可用。运维预防性动作，避免业务方踩到 uncorrectable
3. **走 report-host-as-faulty**：`gcloud compute instances report-host-as-faulty --fault-reasons=behavior=PERFORMANCE,description="high DRAM correctable ECC >1000"`，让 GCE 换 host

`memory/gke_fault_node_physicalhost.md` 里有故障节点上报的规范。

## 常见踩坑（都是别人踩过的，你不用再踩一遍）

1. **wrapper `DONE` marker ≠ test pass** — DCGM/NCCL 在 CUDA busy 情况下 wrapper 判 pass 但 detail log 全 fail。**永远看 detail log**（`qa/analyze-logs.sh` 或直接 grep `Traceback|Fail|busy`）
2. **不要 delete namespace / pod 前先拉日志** — Cloud Logging 有 ~60s flush delay，pod 删了就没了（`memory/log_pull_before_delete_gate.md`）
3. **每次 GCP 操作立即记 `docs/operations.md`** — 交付文档的依据（`memory/ops_log_discipline.md`）
4. **不要并行 5 subblock all-full** — 之前踩过，DRA 层撞车导致 CUDA busy 假报
5. **pool NODE_VERSION nominal ≠ 节点实际 kubelet** — 老 pool 的 NODE_VERSION 显示 4681000 但实际节点还是 4447000
6. **MIG 的 regional instance template 才是决定 COS 镜像的**（不是 pool NODE_VERSION）。核对用 `--verify-only`
7. **pod 1/1 Running 不代表有负载** — `memory/fake_running_zombie_workload.md`，容器 entrypoint 有 `sleep infinity` 兜底
8. **老 pool（pool-0002 / 0006）的 MIG 已指向坏 COS** — 硬件故障触发 MIG 补建会出坏节点
9. **freeze-node-upgrades-ko-regression 到期 2026-10-23** — 到期前 NVIDIA/GKE 若没出 fix 需重评估
10. **`release_channel` 内不是"必须 auto-upgrade"** — `--no-enable-autoupgrade` 可以生效（脚本 `do_create_pool` 已加 fallback）
